Where does LVCE’s
memory actually go?

A plain-text file still starts a sizeable application: four Node services, seventeen web workers, and a full Chromium renderer. Here is what the measurements explain—and what they don’t.

Headline: three uncapped runs per app on the same CI host, Electron 43.1.0, LVCE v0.114.2. These are workload observations, not universal memory requirements. Changing the controls below changes the tables, not these headline cards.

The largest opportunities are startup service activation and worker architecture. Main-process JavaScript is small; source minification alone is not demonstrated to close the gap. Disabling Git is measured as an ablation, while consolidating workers remains a design proposal.

01 / Measured footprint

Compare the whole application, then its parts.

The original published benchmark currently records 578.8 MiB PSS for LVCE, 469.8 for Atom, 374.7 for Zed, and 316.8 for basic Electron. Its capture is September 13; the screenshot motivating this investigation is a different capture. The values below are recomputed from raw trials, not transcribed from the chart.

{{CHART}}
{{ROLES}}

In the matched CI run, the four Node services account for 173.8 MiB PSS. The renderer and workers account for 187.4 MiB, versus 57.7 MiB in basic Electron: about 129.7 MiB extra. Main-process PSS is 88.4 versus 84.4 MiB. Shared-page redistribution offsets some of these additions, yielding the whole-app gap of 287.3 MiB.

How to read the gap: the extra Node services have their own heaps and native runtime state. Renderer PSS includes all seventeen web workers, DOM, Blink, V8, stacks, buffers, code, and allocated-but-unused heap capacity. These categories must not be added again to renderer PSS.

Historical process samples contain only comm=lvce. They cannot reliably identify roles. Our observer additionally records command lines, parent PIDs, thread names and anonymous/file/shared PSS. Electron’s app.getAppMetrics(), in a separate diagnostic run, resolves utility service names. Electron API reference.

02 / A baseline, not a floor

317 MiB and 133 MiB describe different things.

PSS versus enforced budget

The published basic app’s 316.8 MiB is its uncapped idle PSS. 133 MiB is the lowest tested cgroup limit that passed the launch/edit/save protocol in all three runs. Cgroup charging and PSS attribute shared pages differently; archive extraction and retained OS caches also affect which group first owns file pages. This is why the cap can be below PSS. Neither number is a minimum host-RAM requirement. Linux cgroup v2.

The runtime must match

The original minimal app uses Electron 40.0.0; LVCE bundles 43.1.0. Our matched baseline copies the exact checksum-verified LVCE runtime and replaces only its application resources with the minimal editor. It still opens, edits and saves the same file. A richer app is expected to add costs to this configuration, but no definition forces every Electron app to stay above the old measured value.

Use PSS and USS together to judge the resident footprint. Summed RSS double-counts shared mappings; virtual address space is not resident memory. Use cgroup limits to answer the separate question “does this workload survive this budget without swap?” Linux /proc documentation.

Zed’s published PSS is a useful reference, but it ran on another CI machine and uses a different rendering/runtime stack. Beating it is a testable target, not an outcome established by this investigation. A hardware-GPU desktop may rank applications differently from Xvfb/Mesa software rendering.

03 / Change one variable

Experiments with working edit/save checks.

{{EXPERIMENTS}}

Git disabled: −45.7 MiB PSS. LVCE drops from 582.6 to 536.9 MiB, with 9 processes and 15 workers instead of 10 and 17. Basic Electron also drifts down 3.1 MiB in that job, so treat roughly 43–46 MiB as an opportunity estimate, not an exact guaranteed product saving.

20 empty workers: +38.6 MiB PSS. This provides direct evidence of worker runtime cost even when the workers do no useful work.

Minification: no demonstrated memory reduction. JavaScript shrinks from 44.0 to 27.4 MiB on disk (37.8%), but LVCE PSS changes by +2.2 MiB; the unchanged basic control also increases by +2.0 MiB. The difference is too small and confounded by drift to call a meaningful regression or improvement.

Minification

Transform all shipped JavaScript with pinned esbuild, retaining function/class names and preserving module boundaries. No bundling, code splitting, import removal, source-map loading, or product refactoring is added. The preparation JSON records original/transformed bytes and hashes. Passing the plain-text probe establishes only that workload’s behavior; it does not certify every feature after minification.

A smaller file is not an equally smaller heap: V8 compiles source, objects still exist, worker isolates still start, and native allocations remain. Name preservation can itself add code. Inspect the measured result before deciding whether the packaging change is worthwhile.

Twenty empty workers

Add twenty retained, idle dedicated workers to the minimal app. Process count stays at six, while renderer memory increases. This isolates the cost of worker runtimes in this environment. It is not a measurement of each LVCE worker and does not prove that merging seventeen real workers saves seventeen times an empty-worker cost. Electron process model.

Disable built-in Git

Set disabled: true in the packaged built-in Git manifest before launch. No Git repository or Git command is part of the workload. The intervention tests the combined cost of its Node process, workers, UI contributions and initialization. It removes functionality, so it is an estimate of opportunity for more selective activation, not a production fix.

Controls and limits

Each intervention has three unmodified control trials and three changed trials per app on its own runner. Apps/trial order are shuffled with seed 1729 within each block; control runs precede intervention runs. Warm-cache/time drift remains possible. Ranges are run-median ranges, not confidence intervals. Compare each experiment to its matching control; do not subtract two unrelated runners as a causal estimate.

04 / Inside the renderer

Seventeen workers do not mean seventeen processes.

The diagnostic attaches recursively to existing worker targets and asks each V8 isolate for heap usage. The table is a separate local probe; debugger attachment changes memory and it is excluded from benchmark totals. The optional forced-GC column distinguishes allocated objects from those surviving a collection. It is not a proposed runtime optimization.

{{WORKERS}}

A useful correction: extension management had about 12 MiB of used heap in the first diagnostic, but that was not proof of 12 MiB retained. In a later diagnostic it fell from about 5.1 to 0.9 MiB after collection; all seventeen workers together retained about 11.8 MiB of reported JS heap after GC. Heap timing varies substantially. This makes “the renderer is large because live JavaScript objects alone are huge” an incomplete explanation.

The page’s own heap was only a few MiB, and the original diagnostic counted 1,144 DOM nodes and 310 event listeners. Those counts neither prove a leak nor account for all renderer allocations. Worker heaps exclude native Blink/V8 structures, thread stacks, graphics and parts of backing storage. A complete allocation-level explanation of the remaining renderer PSS needs native memory tracing and repeated lifecycle tests.

Named services observed in the diagnostic

A separate CI diagnostic measured median PSS of 58.7 MiB for shared-process, 35.2 MiB for filesystem, 38.7 MiB for the Git Node service, and 39.5 MiB for the watcher. These are instrumented observations, not additional costs to add to the comparison table. Full PID mappings are in diagnostic-ci.json.

  • shared-process: Node utility for shared application services.
  • File System Process: Node utility for filesystem operations.
  • File Watcher Process: Node utility for watching files.
  • Extension builtin.git: Git: a separate Node utility, plus gitMain.js and gitWorkerMain.js web workers.

The diagnostic URL includes a workspace parameter for the fixture’s parent directory even though the benchmark passes only a single file. “No project folder supplied” is therefore not the same as “LVCE initializes no workspace services.”

05 / Code size

Shipped code is not the same as loaded code.

The verified release contains about 44 MiB of JavaScript across 1,431 files. Its main-process bundle is only about 226 KiB; the renderer-worker bundle is about 1.24 MiB. Much of the largest shipped code belongs to optional TypeScript, Prettier, ESLint and preview features. File size alone does not establish that any of it is resident in this plain-text workload.

The build helper defaults to minify = false; the published files are readable. That confirms the packaging premise, but not its memory impact. The paired minification experiment is the evidence for impact. Pinned build helper · Release inventory and hashes.

Target the gap to the matched basic app. Report every candidate’s PSS, USS, startup peak, process/worker counts and typing latency. Neither killing services, regularly forcing GC, disabling the sandbox, nor setting a small V8 heap cap is a validated product solution here.

07 / Reproduce & audit

The report is generated from versioned evidence.

Run the memory investigation in GitHub Actions. The repository pins the LVCE archive checksum and vendors the benchmark at commit 03c3570986eb4c6574d36283361557e50920b902. CI uses Ubuntu 24.04, Xvfb 1280×720, Openbox, Mesa software rendering, fresh isolated XDG profiles and an application cgroup with swap disabled. Real user HOME is preserved; XDG config/data/cache/state and Chromium user data are isolated.

Ten seconds of settling, an exact edit/save/restore readiness check, ten one-second idle samples, then three more edit/save/restore checks. The whole cgroup is stopped after every trial. No user extensions, artificial host pressure or cache dropping. Reparented helpers stay measured; incomplete process snapshots are rejected. Debugger/GC probes run separately. The host, flags, failures, execution order, kernel counters, raw samples and originating Actions URL stay in the JSON.
