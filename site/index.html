02 / A baseline, not a floor

317 MiB and 133 MiB describe different things.

PSS versus enforced budget

The historical Electron 40 basic app’s 316.8 MiB is its uncapped idle PSS. 133 MiB is the lowest tested cgroup limit that passed the launch/edit/save protocol in all three runs. Cgroup charging and PSS attribute shared pages differently; archive extraction and retained OS caches also affect which group first owns file pages. This is why the cap can be below PSS. Neither number is a minimum host-RAM requirement. Linux cgroup v2.

The runtime must match

The original minimal app uses Electron 40.0.0; LVCE bundles 43.1.0. The current comparison preserves LVCE v0.114.2 application resources but replaces its complete runtime with checksum-pinned Electron 44.3.0. The basic app uses that same archive. This is explicitly a runtime override, not an unmodified official LVCE binary. It still opens, edits and saves the same file. A richer app is expected to add costs to this configuration, but no definition forces every Electron app to stay above the old measured value.

Use PSS and USS together to judge the resident footprint. Summed RSS double-counts shared mappings; virtual address space is not resident memory. Use cgroup limits to answer the separate question “does this workload survive this budget without swap?” Linux /proc documentation.

Zed’s published PSS is a useful reference, but it ran on another CI machine and uses a different rendering/runtime stack. Beating it is a testable target, not an outcome established by this investigation. A hardware-GPU desktop may rank applications differently from Xvfb/Mesa software rendering.

03 / Change one variable

Experiments with working edit/save checks.

{{EXPERIMENTS}}
{{EXPERIMENT_SUMMARY}}

Minification

Transform all shipped JavaScript with pinned esbuild, retaining function/class names and preserving module boundaries. No bundling, code splitting, import removal, source-map loading, or product refactoring is added. The preparation JSON records original/transformed bytes and hashes. Passing the plain-text probe establishes only that workload’s behavior; it does not certify every feature after minification.

A smaller file is not an equally smaller heap: V8 compiles source, objects still exist, worker isolates still start, and native allocations remain. Name preservation can itself add code. Inspect the measured result before deciding whether the packaging change is worthwhile.

Twenty empty workers

Add twenty retained, idle dedicated workers to the minimal app. Process count stays at six, while renderer memory increases. This isolates the cost of worker runtimes in this environment. It is not a measurement of each LVCE worker and does not prove that merging seventeen real workers saves seventeen times an empty-worker cost. Electron process model.

Disable built-in Git

Set disabled: true in the packaged built-in Git manifest before launch. No Git repository or Git command is part of the workload. The intervention tests the combined cost of its Node process, workers, UI contributions and initialization. It removes functionality, so it is an estimate of opportunity for more selective activation, not a production fix.

Controls and limits

Each intervention has three unmodified control trials and three changed trials per app on its own runner. Apps/trial order are shuffled with seed 1729 within each block; control runs precede intervention runs. Warm-cache/time drift remains possible. Ranges are run-median ranges, not confidence intervals. Compare each experiment to its matching control; do not subtract two unrelated runners as a causal estimate.

Production build / actual interventions

Patch the shipped app, then measure what still works.

{{PATCH_EXPERIMENTS}}

Shared and filesystem services in main

Replace the selected utilityProcess.fork calls with MessageChannelMain endpoints. The original service code and asynchronous RPC remain, with a separate process facade for each service’s arguments, parent port and listeners. The second variant also moves the filesystem service into main. File watching and Git keep their original processes.

This tests the cost of separate runtimes while retaining the exercised work. Useful service data moves into main, so the removed process’s entire PSS is not recoverable. Synchronous service work now competes with Electron main. Restart, crash recovery, multi-window behavior, large-tree watching and long sessions need dedicated acceptance tests before a product change. Electron MessageChannelMain.

Workers as lazy renderer chunks

Generate an ES module chunk for each packaged core worker and the built-in Git workers. A Worker-compatible endpoint loads the chunk only when the existing code asks to launch that worker. Each invocation keeps its own module variables and real message ports; all execution shares the renderer event loop. The diagnostic asserts zero native web-worker targets and records the chunks actually loaded.

The prototype adapts worker globals, font access and native function bindings, registers generated files in the production allowlist, and permits same-origin fetches in the document’s content security policy. It changes the isolation boundary. The measured path is opening and editing a small file; optional extension workers, heavy syntax work, teardown and responsiveness during blocking work are not validated. Chunking does not by itself postpone services that the current startup immediately requests.

Repository-aware Git activation

Keep Git enabled. Before automatic activation or source-control provider discovery starts it, check the workspace and parents for a .git directory or worktree marker file. Explicit Git commands can still activate it. Negative results are not cached, so later activation requests can discover a newly created repository. Separate fresh-repository trials and diagnostics verify that Git’s Node service and workers return.

This is an activation guard, not a complete repository watcher: it does not independently generate an activation event after an external git init. Remote/virtual workspaces need provider-specific detection. The current positive control proves activation and editing, not every Git command or decoration.

Rollup and Terser without source maps

Run the already bundled main entry through Rollup, preserving its external imports, then minify the shipped JavaScript with Terser compression and identifier mangling. Determine module parsing from the nearest package manifest, including top-level-await modules. Keep function/class names for the app’s dynamic dispatch and error stacks; do not mangle properties. Remove source maps and emit none. Per-file sizes and before/after hashes are recorded.

This is a bounded packaging experiment, not a whole-application rebundle or a property-mangling experiment. Compare resident memory against its own control; disk compression is reported separately. Rollup API · Terser API.

What the failed prototypes taught us

The first CI attempt showed that guarding activation events alone left Git running: provider discovery independently launched it to ask whether the provider was active. Its plain-file PSS was 591.1 MiB versus 589.4 MiB in its own control, with the Git process still present. Those trials are preserved as activation-only evidence; this was no memory improvement. The final guard also covers provider discovery.

Initial renderer prototypes failed edit/save because generated files were absent from the production allowlist, wrapper names collided with bundle-local declarations, and worker code lacked the expected font/global APIs and same-origin fetch permission. No memory saving is reported for those failed startups. Terser required correct module detection for top-level await and a syntax-preserving expansion of export * as default, which its parser rejected in the shipped yoctocolors dependency.

The combined variant is measured independently. It applies service consolidation, the Git guard, then generates renderer chunks from that changed code. Its result accounts for overlapping savings; adding the individual deltas would not. Every reported variant must pass three uncapped edit/save trials, and a separate diagnostic must confirm the intended architecture. None is presented as a production-ready patch.

05 / Code size

Shipped code is not the same as loaded code.

The verified release contains about 44 MiB of JavaScript across 1,431 files. Its main-process bundle is only about 226 KiB; the renderer-worker bundle is about 1.24 MiB. Much of the largest shipped code belongs to optional TypeScript, Prettier, ESLint and preview features. File size alone does not establish that any of it is resident in this plain-text workload.

The build helper defaults to minify = false; the published files are readable. That confirms the packaging premise, but not its memory impact. The paired minification experiment is the evidence for impact. Pinned build helper · Release inventory and hashes.

07 / Reproduce & audit

The report is generated from versioned evidence.

Run the memory investigation in GitHub Actions. The repository pins the LVCE archive checksum and vendors the benchmark at commit 03c3570986eb4c6574d36283361557e50920b902. CI uses Ubuntu 24.04, Xvfb 1280×720, Openbox, Mesa software rendering, fresh isolated XDG profiles and an application cgroup with swap disabled. Real user HOME is preserved; XDG config/data/cache/state and Chromium user data are isolated.

Ten seconds of settling, an exact edit/save/restore readiness check, ten one-second idle samples, then three more edit/save/restore checks. The whole cgroup is stopped after every trial. No user extensions, artificial host pressure or cache dropping. Reparented helpers stay measured; incomplete process snapshots are rejected. Debugger/GC probes run separately. The host, flags, failures, execution order, kernel counters, raw samples and originating Actions URL stay in the JSON.
